## AI-Native Development

AI가 만든 결과는 타입, 테스트, 화면 검증과 직접 검수를 거쳐 적용합니다.

- **멀티 에이전트 번역 파이프라인 설계**: 단일 프롬프트 번역은 결과 품질이 매번 들쭉날쭉했습니다. 번역, 한국어 품질 검토, 원문 충실도 검증을 전담 에이전트로 나누고 단계마다 승인 게이트를 두어 한 번의 생성 결과에 품질이 좌우되지 않도록 재구성했습니다 ([관련 글](https://caesiumy.dev/posts/ai/ai-translation-orchestration))
- **MCP 기반 개발 환경 통합**: 디자인을 화면 코드로 옮기고 이슈를 PR로 이어가는 반복 작업에 매번 시간이 샜습니다. Figma, Linear, Chrome DevTools를 MCP로 연동하고 사람이 판단할 지점만 남기도록 승인 게이트를 재설계해 반복 노동을 걷어냈습니다 ([Figma 연동](https://caesiumy.dev/posts/ai/mcp-figma-ui-generation) | [이슈→PR](https://caesiumy.dev/posts/ai/linear-mcp-slack-ticket-automation))
- **E2E 자동화 스킬 제작 후 실무 투입(e2e-flow-skill)**: QA 인력이 없어 E2E 도입이 계속 밀렸습니다. 자연어 시나리오 생성과 실패 trace 기반 자가 복구를 스킬로 만들어 외주 API 이관 검증에 실제 투입했습니다 ([GitHub](https://github.com/CaesiumY/e2e-flow-skill))
- **오픈소스 Claude Code 알림 플러그인(dding-dong) 설계와 배포**: 여러 세션을 동시에 돌리면 작업 완료와 입력 요청을 알 수 없어 컴퓨터 앞을 지켜야 했습니다. 크로스 플랫폼(macOS/Linux/WSL) 훅과 TTS로 OS별 알림 차이를 흡수하고, 마켓플레이스, 설치 스킬, 랜딩 페이지를 묶어 배포해 진입 장벽을 낮췄습니다 ([랜딩](https://caesiumy.dev/dding-dong/) | [GitHub](https://github.com/CaesiumY/dding-dong))

**프리랜서 | 유저 페이지, 관리자 페이지 프론트엔드 개발 (2024.05 ~ 2026.05, 2년)**

유저, 관리자 앱의 전반적인 개발과 공통 구조 설계를 담당했습니다. 프론트엔드 개발자 2명 중 동료는 에디터 등 특정 기능을 맡았고, 고객마다 디자인과 기능이 다른 앱을 함께 운영했습니다.

- **모노레포 아키텍처 설계와 공통화 경계(Turborepo, FSD)**
  - **상황**: 동일 기능을 고객마다 다른 UI로 배포하는 특성상, 유저 모노레포(8+ 앱), 관리자, 대시보드 3개 레포에서 같은 로직을 앱마다 따로 고쳐야 했습니다
  - **선택한 이유**: 중복 수정 비용을 줄이기 위해 Turborepo 기반 구조를 제안하고 구축했습니다. 인증, 공통 UI, 테스트처럼 모든 앱이 같아야 하는 부분은 Core 패키지로 추출하고, 브랜드마다 달라야 하는 스타일은 앱의 토큰 오버라이드로 분리해 공통화 경계를 정했습니다
  - **검증과 결과**: 공통 속성을 지우자 다른 앱의 빌드가 깨진 일을 계기로 검증 범위를 넓히고, 재사용하는 E2E 모듈을 파일럿 검증한 뒤 앱들에 적용했습니다. 공통 수정 1회가 8+ 앱에 일괄 반영되고 신규 앱 셋업 시간과 중복 코드가 줄었습니다
- **API 클라이언트 점진적 이관(Orval)**
  - **상황**: Swagger가 자주 바뀌어 문서를 보며 타입에 수기로 반영하는 반복 비용이 컸습니다
  - **선택한 이유**: 초기 AI 일괄 이관에서 회귀를 발견해, 한 번에 바꾸는 대신 엔드포인트 단위 `자동 생성 → 기존 요청/응답과 호환성 대조 → 이관 → Vitest, RTL, Playwright 검증` 루프로 범위를 좁혀 확장하는 방식을 택했습니다
  - **검증과 결과**: 검증을 통과한 API만 다음 대상으로 넘기며 약 100개 엔드포인트를 이관하고 운영에도 나눠 배포했습니다. 신규 연동은 명령어 1회로 대체됩니다
- **API 변경 대응 절차 정착**: 기능 개발, 테스트, 배포 전에 최신 스키마로 코드를 재생성하도록 워크플로우에 통합했습니다. AI가 변경점과 작업 계획을 제시하면 직접 승인한 뒤 진행하도록 구성해, 자동 생성과 변경 판단을 분리했습니다
- **디자인 시스템을 AI로 생성하고 검수하는 파이프라인 구축**(설계와 운영 전담)
  - **상황**: 다중 브랜드 앱마다 Figma 노드를 반복해서 전달해야 했고, AI가 생성하는 컴포넌트 구조는 매번 달라졌습니다
  - **선택한 이유**: Figma 노드 전달을 SSOT JSON 매핑으로 정리해 멱등성을 확보하고 Storybook, 디자인 토큰 생성에 연결했습니다. 구조가 흔들리는 문제는 모범 사례 기반 정적 검사로 컴포넌트 누락과 과잉을 확인하고 AI가 수정하는 루프로 대응했습니다
  - **검증과 결과**: 타입, 빌드 검사와 Playwright MCP 화면 확인 후 직접 검수했습니다. 공통 구조 재사용과 AI 활용으로 신규 앱 개발을 예상 3개월 대비 실제 3주에 완료했습니다
- **선언적 폴백과 위젯 단위 오류 격리**: 개발 환경에서 API 하나가 실패하면 화면 전체가 무너졌고, 화면마다 로딩과 에러 분기를 수기로 달아야 했습니다. Suspensive와 ErrorBoundary를 개별 위젯에 적용해 추천 게시글 조회가 실패해도 해당 영역만 오류 화면으로 전환되고 나머지는 정상 동작하게 했고, 화면별 분기 코드를 걷어냈습니다

**프론트엔드 엔지니어 (2022.03 ~ 2023.09, 1년 6개월)**

- **실시간 데이터 계약의 단일 공급원(gRPC, Protobuf)**
  - **상황**: 프론트엔드와 백엔드가 바이너리 데이터 매핑을 각자 관리해 타입 안정성이 없었고, 모노레포가 아니라 양쪽 레포의 스키마 동기화도 까다로웠습니다
  - **선택한 이유**: 중복 관리를 없애기 위해 gRPC와 Protobuf 도입을 제안하고 데이터 계약을 명시적인 스키마로 정의했습니다. 스키마는 S3와 CDN을 단일 공급원으로 삼아 양쪽이 같은 원본을 바라보게 했습니다
  - **검증과 결과**: 빌드 전에 최신 스키마를 자동으로 내려받아 반영하게 해 타입 안정성을 확보했고, 동료들에게 README 사용 가이드를 배포했습니다
- **상태관리 최적화**: 실시간 시뮬레이터의 React HUD에서 프레임마다 갱신되는 데이터 때문에 자주 바뀌지 않는 컴포넌트까지 리렌더됐습니다. Redux Toolkit(RTK) 슬라이스를 **갱신 주기 기준으로 분리**해 구독 범위를 좁혔고, React 개발자 도구의 렌더링 하이라이트로 비실시간 영역이 프레임 단위 리렌더에서 빠진 것을 확인했습니다
- **CRA(craco)→Vite 마이그레이션과 클래스→함수형 전환**: eject로 웹팩 설정이 노출된 채 craco로 덮어쓰는 비표준 환경이라 설정이 복잡하고 대기 시간이 길었습니다. Vite 전환을 제안하고 마이그레이션을 맡아 개발 서버 시작과 배포용 빌드 시간을 줄였습니다. 함수형 전환에서는 Hook의 유용성과 React의 발전 방향을 근거로 팀 합의를 이끌었습니다
- **다국어 번역 파일의 배포 구조 개선**: 번역 파일이 프로젝트 내부에 있어 문구 수정마다 개발자 배포가 필요했습니다. S3와 CDN으로 분리 제공해 비개발자도 업로드만으로 즉시 반영할 수 있게 됐고 렌더링도 빨라졌습니다
- **커스텀 디자인 시스템 구축**: 파편화된 CSS로 스타일이 제각각이던 문제를 MUI 토큰을 오버라이드한 공통 컴포넌트로 정리해 신규 화면 개발 속도가 빨라지고 스타일 불일치 지적이 줄었습니다. RHF/Zod 폼도 통일하고 GitHub PR 템플릿과 필수 리뷰어 규칙으로 코드 리뷰 문화를 도입했습니다
- **사내 블로그 구축**: 비개발자가 콘텐츠를 관리할 수 있도록 Notion API CMS로 사내 블로그를 구축하고, 빌드 단계 이미지 최적화를 도입해 개발자 없이 등록, 수정하게 했습니다

프리랜서 프로젝트는 일부 재직, 교육 활동 기간과 병행했습니다.
