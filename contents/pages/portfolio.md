## 케이스 스터디

### §1. API 클라이언트 점진적 마이그레이션 (한국기술마켓, 프론트엔드 엔지니어)

**문제**

- Swagger 문서를 보고 TypeScript 타입 코드를 사람이 직접 작성해 스키마를 관리하고 있었습니다. 데이터나 기능이 추가될 때마다 같은 작업을 처음부터 다시 해야 했고, 이 반복이 API 연동의 상시 비용으로 누적되고 있었습니다.

**해결**

- Orval 도입을 먼저 제안하였습니다. 모노레포에 API 클라이언트 패키지를 신설하고 자동 생성물을 그 패키지 안으로 격리해, 생성 코드와 사람이 작성하는 코드의 경계를 분명히 하였습니다.
- 전체를 한 번에 교체하지 않고 하네스 엔지니어링 개념으로 엔드포인트 단위의 점진적 이관을 설계하였습니다. 엔드포인트 하나마다 ① Orval로 자동 생성 → ② 실제 호출 응답과 기존 레거시 타입의 호환성 대조 → ③ 호환되면 이관 적용 → ④ 유닛 테스트와 E2E 테스트를 추가해 검증하는 네 단계를 거쳤습니다.
- 이 루프의 목적은 속도가 아니라 결정성이었습니다. 사람이 문서를 읽고 판단하던 자리를 명령어 하나로 대체하되, 그 명령어가 스키마 검증과 테스트 통과까지 책임지는 게이트로 작동하게 하였습니다.
- 엔드포인트 수가 예상보다 많아 전체 소요가 길어졌고, 그 과정에서 일부 구간은 진행 효율을 타협해야 했습니다. 이관 중 구버전과 신버전이 공존하는 기간의 안전성을 우선한 판단이었습니다.

**결과**

- **약 100개 엔드포인트**(추정)를 서비스 중단 없이 이관하였고, 신규 API 연동은 수기 스키마 작성 공정 없이 **명령어 1회**로 대체되었습니다.
- 이관된 엔드포인트마다 유닛 테스트와 E2E 테스트가 함께 남아, 이후 스키마 변경이 테스트에서 먼저 걸리는 구조가 되었습니다.

**러닝 포인트**

- 처음에는 기술 블로그의 대규모 마이그레이션 사례를 보고 AI에게 일괄 처리를 맡기면 끝날 것이라 예상했지만, 한 번에 처리하는 방식은 성립하지 않았습니다. 방향을 바꿔 AI와 함께 검증 게이트를 설계했고, 규모가 큰 이관일수록 **자동화해야 할 대상은 작업 자체가 아니라 작업의 검증**이라는 것을 배웠습니다.

### §2. AI-Native 개발 환경 구축 (한국기술마켓, 프론트엔드 엔지니어, 2년)

**문제**

- 다중 브랜드 확장 시 동일 패턴 반복 작업이 신규 브랜드 한 개당 약 3주씩 소요되어 외주 워크플로우의 핵심 병목이었습니다.
- 테스트 샘플 페이지 단독 검증 방식은 위젯 누락이나 MCP 미호출 등 비결정성이 심해, 20번 이상 시도해도 멱등성 보장이 어려웠습니다.

**해결**

- 파운데이션에서 빌드로 이어지는 2중 구조 파이프라인을 설계하였습니다. 파운데이션은 흩어진 피그마 노드 ID를 SSOT JSON으로 저장해 멱등성을 보장하고, 빌드 단계는 라우트별 PRD를 생성한 뒤 서브 에이전트가 독립 환경에서 병렬로 페이지를 조합합니다.
- 디자인 시스템 검증 레이어로 스토리북을 도입하였습니다. 단순 검증 도구가 아니라 추상화 레이어로 작동시켜 AI 출력 비결정성을 통제하는 것이 목적이었습니다.
- 유저 앱, 관리자, 대시보드 등 서로 다른 3개 레포에서 동일하게 사용해야 했기에 kotech-plugin을 별도 레포로 분리하여 설치형으로 구성하였습니다. 독립성은 향상되었으나 테스트 플라이트에서 발견된 이슈를 곧바로 플러그인에 반영하기 어려운 트레이드오프가 발생했습니다.
- 이를 양방향 자동화 스킬로 보완하였습니다. 적용 레포 측 "이슈 보고 스킬"이 테스트 플라이트 결과에서 발견된 이슈를 플러그인 레포에 GitHub 이슈로 자동 발행하면, 플러그인 레포 측 "이슈 해결 스킬"이 해당 이슈를 호출해 수정 작업을 진행하는 사이클로 운영됩니다.

**결과**

- 신규 브랜드 출시 공수 **3주 → 3일**, 디자인 시스템 만족 결과 시도 횟수 **20회 → 약 2회**로 개선되었습니다.
- 3개 레포(유저 모노레포 8+ 앱, 관리자, 대시보드) 운영의 핵심 인프라로 자리 잡았습니다.

**러닝 포인트**

- 공용 모듈을 별도 레포로 떼어내면 독립성은 얻지만 피드백 경로가 끊긴다는 것을 겪었습니다. 분리 자체를 되돌리는 대신 끊긴 경로를 자동화로 다시 이은 경험에서, 구조적 선택의 비용은 **선택을 철회하기보다 보완 장치로 상쇄하는 편**이 낫다는 판단 기준을 얻었습니다.

### §3. 빌드 환경 현대화 (KC Softmax, 프론트엔드 엔지니어, 1년 6개월)

**문제**

- 당시 CRA가 eject로 웹팩 설정을 노출하고 craco로 덮어씌운 비표준 환경이었습니다. 설정 추적이 어려웠고, 무엇보다 개발 서버와 빌드 속도가 현저히 느려 DX에 직접 영향을 주고 있었습니다.

**해결**

- 검토한 두 대안은 (1) Vite로의 진보, (2) 웹팩 설정을 되돌려 순정 CRA로 회귀하는 것이었습니다. 속도 이슈 해결을 우선 목표로 두고, 가장 빠르다고 평가받고 생태계에서 떠오르고 있던 Vite를 채택하였습니다.
- 누적된 craco 비표준 환경 정리가 마이그레이션과 동시에 이루어지면서 기술 부채를 함께 해소하였습니다.
- 클래스 컴포넌트에서 함수형으로의 전환은 Hook 유용성과 React 발전 방향을 근거로 팀 합의를 도출하였습니다.
- 복잡한 전역 상태로 인한 불필요 리렌더링은 RTK 슬라이스 분리로 해결하였고, 바이너리 값으로 운영되던 실시간 데이터 동기화는 gRPC/Protobuf 스트리밍으로 전환해 타입 안정성과 가독성을 확보하였습니다.

**결과**

- 빌드 시간이 **70% 단축**되었습니다(빌드 출력 기준 실측). 비표준 빌드 환경 정리로 DX가 회복되었습니다.

**러닝 포인트**

- 사전에는 큰 작업이라 예상해 단계적 진행을 염두에 뒀지만, 실제 Vite 마이그레이션은 예상보다 수월해 한 번에 완료했습니다. **이관 규모는 코드 양이 아니라 검증해야 할 경계면의 수로 정해진다**는 것을 이때 처음 체감했고, 이 기준이 §1에서 엔드포인트 단위로 쪼개는 판단의 근거가 되었습니다.

### §4. 백엔드 의존성 제거 (교육 지원 플랫폼, 1개월 개발 + 7개월 유지보수)

**문제**

- 클라이언트의 잦은 기획 변경 환경에서 백엔드 API 설계가 매번 프론트엔드 진행을 가로막았습니다. API 미완성 상태로는 화면 검증이나 UI 분기 테스트도 불가능했습니다.

**해결**

- MSW로 API 스키마를 프론트엔드에서 선제 정의해 백엔드에 역제안하는 워크플로우를 도입하였습니다. 이는 일정 단축뿐 아니라 백엔드 결정의 근거 검증 자산으로 작동했습니다. 백엔드가 사전 협의 없이 ID를 숫자형으로 변경 요청했을 때 JS Max Integer 한계를 근거로 즉시 역제안할 수 있었습니다.
- 스키마가 확정된 뒤에는 Orval로 API 클라이언트와 TanStack Query 코드를 자동 생성해 데이터 페칭 보일러플레이트를 흡수하였습니다. 여러 코드 제너레이터를 비교한 끝에 React 기반 스택과 가장 잘 맞는다고 판단한 선택이었습니다. 자동 생성 코드가 기능별 폴더에 함께 놓이지 못하는 응집성 손실이 있었지만, 사람이 직접 손댈 일이 거의 없는 코드이므로 수용 가능한 비용이라고 보았습니다.

**결과**

- 개발 공수 **2개월 → 1개월**로 단축되었으며(50% 단축, 납품 기준 측정), 유지보수 포함 **8개월 계약을 완수**하였습니다.

**러닝 포인트**

- 선제 스키마 정의의 실질적 가치가 일정 단축이 아니라 **협업에서의 근거 확보**에 있다는 것을 알게 되었습니다. 미리 만들어 둔 스키마가 있으면 상대 결정에 반대할 때 의견이 아니라 검증 가능한 자료로 말할 수 있었습니다.

### §5. 번역 파이프라인 에이전트 오케스트레이션 (사이드 프로젝트, 2026)

**문제**

- 영문 기술 글을 한국어로 옮기는 작업은 번역, 번역투 교정, 원문 대조, 문장 다듬기가 매번 같은 순서로 반복되는데, 이를 한 번에 처리하면 품질이 시도마다 달라졌습니다. 특히 "잘 읽히는가"와 "원문에 충실한가"는 서로 당기는 기준이라, 한 주체가 동시에 판단하면 한쪽이 밀렸습니다.

**해결**

- 역할을 쪼개 6개 전담 에이전트로 분리하고, 메인 루프는 조율만 담당하는 오케스트레이터-워커 구조로 설계하였습니다. 메인 루프는 인자 파싱, 게이트, 점수 판정, 최종 반영만 하고 번역과 채점은 직접 하지 않습니다.
- 상충하는 두 기준을 **서로 다른 에이전트에 맡겼습니다.** 한국어 품질 검토자는 번역투와 가독성을 4개 가중 차원으로, 원문 충실도 검증자는 의미와 기술 정확성, 뉘앙스를 3개 차원으로 채점하며 하드 임계값 미달 시 독립적으로 FAIL을 냅니다. 두 검증은 서로 의존하지 않으므로 병렬로 호출합니다.
- 28개 번역투 패턴은 참조 파일 한 곳을 단일 정본으로 두고 패턴 번호를 다른 파일에 복사하지 않도록 했습니다. 같은 기준이 여러 벌 존재하면 시간이 지나며 갈라지기 때문입니다.
- 에이전트별 모델은 정의 파일의 별칭(haiku, sonnet, opus)으로 지정해 작업 난이도에 맞췄습니다. 문장 단위 패턴 검사는 경량 모델, 원문 대조 검증은 상위 모델이 담당합니다.

**결과**

- 이 파이프라인을 거쳐 발행한 번역글은 **11편**입니다(블로그 전체 번역글 19편 중). 발행 분류 일관성은 CI 검사로 강제됩니다.
- 품질 판정이 사람의 인상이 아니라 차원별 점수와 임계값으로 남아, 미달 시 어느 축이 부족한지가 지시로 바로 나옵니다.

**러닝 포인트**

- 처음에는 상위 모델 하나가 전 과정을 처리하는 편이 품질에 유리할 것이라 보고 메인 루프가 번역과 채점까지 직접 했습니다. 그런데 **스스로 만든 결과물을 스스로 채점하면 점수가 후해졌습니다.** 조율과 실행을 분리하고 채점을 별도 에이전트로 떼어낸 뒤에야 점수가 신뢰할 만해졌고, 검증 주체는 작업 주체와 분리되어야 한다는 원칙을 얻었습니다. §1에서 이관 판단을 사람이 아닌 테스트에 맡긴 것과 같은 결론입니다.

### §6. 모노레포 아키텍처와 공통 모듈과 Core 패키지 설계 (한국기술마켓, 프론트엔드 엔지니어, 2년)

**문제**

- 동일한 기능에 서로 다른 UI를 배포하는 사업 특성상 유저 모노레포(**8+ 앱**), 관리자, 대시보드 **3개 레포**를 동시에 운영해야 했습니다. Turborepo 단일 구조로 묶어두기는 했지만, 각 앱이 모노레포의 이점을 실제로 활용하지 못한 채 같은 로직을 앱마다 따로 들고 있었습니다.
- 그래서 공통 규칙 하나가 바뀌면 앱 수만큼 같은 수정을 반복해야 했고, 어느 앱이 아직 옛 규칙을 쓰고 있는지가 코드만 봐서는 드러나지 않았습니다.
- 구조를 정리하려고 도입한 FSD는 초기 생산성을 오히려 떨어뜨렸습니다. 레이어 규칙을 지키는 비용을 규칙에서 얻는 이점보다 먼저 체감하는 구간이 있었습니다.
- 화면 단위 안정성에도 같은 종류의 중복이 있었습니다. 위젯 하나의 API 실패가 페이지 전체를 죽였고, 화면마다 로딩과 에러 분기를 수기로 달아 보일러플레이트가 쌓였습니다.

**해결**

- 앱마다 복제되던 공통 로직을 Core 패키지로 추출해 중앙에 모았습니다. 개별 앱은 자기 UI 차이만 들고, 공유하는 규칙은 패키지 한 곳에서만 정의하도록 경계를 다시 그었습니다.
- FSD는 철회하지 않고, 실제로 기능을 추가하는 경로에서 거쳐야 하는 레이어만 남기는 쪽으로 레이어 구조를 우리 사용 흐름에 맞게 커스텀했습니다.
- 로딩과 에러 분기는 Suspense/ErrorBoundary를 공통 경계로 두어 선언적으로 흡수했습니다. 장애 영향 범위를 컴포넌트 단위로 격리해 위젯 하나의 실패가 페이지 전체로 번지지 않도록 경계를 앞당겼습니다.
- 유저 앱은 데스크톱 기준 화면에 미디어쿼리를 더해 모바일과 태블릿까지 대응하는 반응형 웹으로 구현했고, 이 대응 규칙도 앱별로 흩어지지 않게 공통 컴포넌트 쪽에 모아 두었습니다.

**결과**

- 이제 공통 로직은 1회 수정으로 **8+ 앱**에 일괄 반영됩니다. 앱 사이에 복제해두던 코드와 파일이 줄었고, 신규 앱을 붙일 때 처음부터 다시 만드는 범위도 셋업 단위로 좁혔습니다.
- 위젯 하나가 실패해도 페이지 전체가 함께 죽지 않습니다. 화면별로 달아두던 로딩과 에러 분기 코드도 걷어냈습니다.
- 정리한 3개 레포 운영 구조 위에 §2의 AI-Native 파이프라인을 올릴 수 있었습니다.

**러닝 포인트**

- FSD를 도입하고 나서, 규칙을 지키는 일 자체가 목적이 되는 순간부터 아키텍처는 비용으로 돌아왔습니다. 원본 방법론을 그대로 이식한다고 팀 생산성이 오르지는 않았고, 여기서 아키텍처는 목표가 아닌 수단이라는 기준을 얻었습니다. 도입을 철회하지 않고 레이어를 우리 흐름에 맞게 다시 그린 판단도 그 기준에서 나왔습니다.
- 공통 코드를 어디에 둘지는 §2와 반대 방향으로 결정했습니다. §2의 kotech-plugin은 3개 레포가 함께 쓰기 때문에 별도 레포로 분리했지만 피드백 경로가 끊기는 비용을 치렀고, Core 패키지는 소비자가 모두 같은 모노레포 안에 있어 분리하지 않는 편이 맞았습니다. 공유 코드의 배치는 소비자의 경계가 결정한다는 것을 두 경험의 차이에서 배웠습니다.

### §7. AWS 기반 프론트엔드 인프라 개선 (KC Softmax, 프론트엔드 엔지니어)

**문제**

- 다국어 번역 파일(키와 결과값을 매핑한 파일)이 프로젝트 내부에 있었습니다. 단순한 번역 문구 하나를 고칠 때도 개발자가 직접 업데이트하고 기존의 복잡한 배포 프로세스를 거쳐야 해서, 번역 관리 자체가 개발 일정에 묶여 있었습니다.
- gRPC는 프론트엔드와 백엔드가 동일한 스키마 파일을 공유해야 정상 동작하는데, 모노레포 환경이 아니었기 때문에 매번 양쪽 레포지토리에 스키마를 일일이 배포하고 동기화해야 했습니다.

**해결**

- 번역 파일은 S3에 배포하고 CloudFront(CDN)로 제공하는 구조로 분리해, 리소스를 코드 저장소 밖으로 빼면서 번역 수정이 배포 파이프라인을 타지 않게 만들었습니다.
- gRPC 스키마 파일도 같은 방식으로 S3에 올려두고 CDN으로 배포하되, 여기서는 소비 시점까지 파이프라인에 넣었습니다. 프론트엔드와 백엔드 모두 로컬 개발 서버를 실행하거나 빌드할 때 S3에서 최신 스키마를 먼저 내려받아 동기화한 뒤 빌드와 테스트를 진행하도록 구성했습니다.
- 두 조치의 판단 근거는 같았습니다. 여러 저장소가 함께 쓰는 리소스를 코드 안에 두면 저장소 수만큼 사본이 생기니, 리소스를 저장소 밖으로 빼고 CDN을 단일 공급원으로 삼으면 동기화라는 작업 자체가 사라집니다.

**결과**

- 이제 비개발자도 S3에 파일을 업로드하고 수정하기만 하면 번역이 즉시 반영됩니다. CDN 캐싱 덕분에 번역 데이터를 이전보다 빠르게 받아와 렌더링합니다.
- gRPC 스키마는 S3를 단일 진실 공급원(SSOT)으로 삼았고, 그 뒤로는 양쪽이 스키마를 맞출 일 자체가 없어졌습니다.
