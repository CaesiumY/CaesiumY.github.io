# 포트폴리오

## 지원 동기

웹에서 보던 영상을 저장하고 싶었던 적이 있습니다. 그런데 그 영상은 하나의 파일이 아니었습니다.

네트워크 탭을 열어보니 영상은 작은 조각(청크)으로 쪼개져 순서대로 도착했고 익숙한 MP4가 아닌 낯선 형식이었습니다.

> "브라우저에 영상이 보인다면 서버가 데이터를 내려주고 있을 텐데, 이 조각들은 어떻게 이어 붙는 걸까?"

이 질문을 붙들고 조각이 도착하는 규칙을 찾아 순서대로 모아 하나의 영상으로 되살려 봤습니다. 나중에야 이것이 청크 단위로 나눠 전송하는 스트리밍 방식(HLS)이고, 브라우저 대신 청크를 받아 이어 붙여 재생해 주는 라이브러리가 있다는 것도 알았습니다.

그 경험을 계기로, 브라우저가 영상 같은 대용량 데이터를 어떻게 끊김 없이 흘려보내는지에 자연스럽게 관심을 갖게 됐습니다.

## 케이스 스터디

### §1. API 클라이언트 점진적 마이그레이션 (한국기술마켓, 프리랜서 프론트엔드 엔지니어)

> 수기 타입 작성을 엔드포인트 단위 검증 루프로 대체해 약 100개를 무중단 이관, 신규 연동은 명령어 1회로.

**문제**

- **수기 스키마 관리**: Swagger 문서를 보고 TypeScript 타입 코드를 사람이 직접 작성해 스키마를 관리했습니다. 데이터나 기능이 추가될 때마다 같은 작업을 처음부터 다시 해야 했고 이 반복이 API 연동의 상시 비용으로 쌓였습니다.

**해결**

- **생성 코드 격리**: Orval 도입을 먼저 제안하고 모노레포에 API 클라이언트 패키지를 신설해 자동 생성물을 그 안으로 격리하면서 생성 코드와 사람이 작성하는 코드의 경계를 분명히 나눴습니다.
- **엔드포인트 단위 점진 이관**: 전체를 한 번에 교체하는 길은 택하지 않았습니다. 하네스 엔지니어링 개념을 빌려 점진적 이관을 설계했습니다. 엔드포인트 하나마다 ① Orval로 자동 생성 → ② 실제 호출 응답과 기존 레거시 타입의 호환성 대조 → ③ 호환되면 이관 적용 → ④ 유닛 테스트와 E2E 테스트를 추가해 검증하는 네 단계를 거쳤습니다.
- **결정성 중심의 게이트**: 이 루프의 목적은 결정성이었습니다. 사람이 문서를 읽고 판단하던 자리를 명령어 하나로 대체하되 그 명령어가 스키마 검증과 테스트 통과까지 책임지는 게이트로 작동하게 했습니다.
- **공존 기간의 안전성**: 이관 중 구버전과 신버전이 함께 도는 기간을 우선해 속도 대신 결정성을 택한 판단이었습니다.

**결과**

- **무중단 이관과 연동 자동화**: **약 100개 엔드포인트**를 서비스 중단 없이 이관했습니다. 신규 API 연동에서는 수기 스키마 작성 공정을 걷어내고 **명령어 1회**로 대체했습니다.
- **테스트 자산 축적**: 이관한 엔드포인트마다 유닛 테스트와 E2E 테스트를 함께 남겨 이후로는 스키마 변경이 테스트에서 먼저 걸립니다.

**러닝 포인트**

- 처음에는 기술 블로그의 대규모 마이그레이션 사례를 보고 AI에게 일괄 처리를 맡기면 끝날 것이라 예상했습니다. 한 번에 처리하는 방식은 성립하지 않았습니다. 방향을 바꿔 AI와 함께 검증 게이트를 설계했습니다. 규모가 큰 이관일수록 자동화해야 할 대상은 작업 자체가 아니라 작업의 검증입니다.

### §2. AI-Native 개발 환경 구축 (한국기술마켓, 프리랜서 프론트엔드 엔지니어)

> 신규 브랜드 출시 공수 3주 → 3일, 시도 20회 → 약 2회. 브랜드마다 처음부터 반복하던 작업을 SSOT 파운데이션과 스토리북 검증 레이어로 묶은 결과입니다.

**문제**

- **신규 브랜드 반복 공수**: 브랜드를 새로 늘릴 때마다 같은 패턴을 처음부터 반복해야 했고 한 개당 약 3주가 드는 이 공정이 외주 워크플로우의 핵심 병목이었습니다.
- **단일 샘플 검증의 한계**: 테스트 샘플 페이지 하나만 놓고 검증하는 방식은 위젯이 빠지거나 MCP를 호출하지 않는 등 비결정성이 심했습니다. 20번 이상 시도해도 멱등성을 보장하기 어려웠습니다.

**해결**

- **파운데이션과 빌드 분리**: 파이프라인은 파운데이션에서 빌드로 이어지는 2중 구조입니다. 파운데이션은 흩어진 피그마 노드 ID를 SSOT JSON으로 저장해 멱등성을 보장하고 빌드 단계는 라우트별 PRD를 생성한 뒤 서브 에이전트가 독립 환경에서 병렬로 페이지를 조합합니다.
- **AI 출력 비결정성 통제**: 디자인 시스템 검증 레이어로 스토리북을 도입하되 검증 도구로만 쓰지 않고 추상화 레이어로 작동시켜 출력이 흔들리는 폭을 좁히는 것이 목적이었습니다.
- **플러그인 레포 분리**: 유저 앱, 관리자, 대시보드 등 서로 다른 3개 레포가 kotech-plugin을 똑같이 써야 했습니다. 어느 한 레포에 두는 대신 독립 레포에 올려 설치형으로 구성했습니다. 독립성은 얻었지만 테스트 플라이트에서 나온 이슈를 곧바로 플러그인에 반영하기 어려운 트레이드오프가 따라왔습니다.
- **끊긴 피드백 경로 복구**: 양방향 자동화 스킬 두 개가 이 트레이드오프를 상쇄합니다. 적용 레포 측 "이슈 보고 스킬"이 테스트 플라이트에서 나온 이슈를 플러그인 레포에 GitHub 이슈로 자동 발행하면 플러그인 레포 측 "이슈 해결 스킬"이 그 이슈를 받아 수정하는 사이클로 돌립니다.

**결과**

- **출시 공수와 시도 횟수**: 신규 브랜드 출시 공수 **3주 → 3일**, 디자인 시스템 만족 결과 시도 횟수 **20회 → 약 2회**로 줄였습니다.
- **신규 프로젝트 셋업**: 직접 손으로 할 때는 약 3개월이 걸렸지만 AI 에이전트를 도입해 구축하면서 **약 3주**로 줄었습니다.
- **핵심 인프라 안착**: 3개 레포(유저 모노레포 8+ 앱, 관리자, 대시보드) 운영의 핵심 인프라로 자리 잡았습니다.

**러닝 포인트**

- 공용 모듈을 별도 레포로 떼어내면 독립성은 얻지만 피드백 경로가 끊깁니다. 분리 자체를 되돌리는 대신 끊긴 경로를 자동화로 다시 이었습니다. 구조적 선택의 비용은 선택을 철회하기보다 보완 장치로 상쇄하는 편이 낫습니다.

### §3. 백엔드 의존성 제거 (교육 지원 플랫폼, 프리랜서 프론트엔드 엔지니어)

> 백엔드 API를 기다리느라 멈추던 프론트엔드 진행을 선제 스키마 정의로 풀어 2개월 산정 공수를 1개월에 납품.

**문제**

- **백엔드 API 대기 병목**: 클라이언트가 기획을 자주 바꾸는 환경이라 백엔드 API 설계가 매번 프론트엔드 진행을 가로막았습니다. API가 완성되지 않으면 화면 검증이나 UI 분기 테스트도 할 수 없었습니다.

**해결**

- **MSW 선제 스키마 정의**: 백엔드 설계를 기다리는 대신 프론트엔드가 API 계약을 그려 역제안하는 워크플로우를 도입했습니다. 백엔드가 사전 협의 없이 ID를 숫자형으로 변경 요청했을 때 JS Max Integer 한계를 근거로 즉시 역제안할 수 있었습니다.
- **Orval 코드 생성**: 스키마가 확정된 뒤에는 API 클라이언트와 TanStack Query 코드를 자동 생성해 데이터 페칭 보일러플레이트를 흡수했습니다. 여러 코드 제너레이터를 비교해 React 기반 스택과 가장 잘 맞는 쪽을 골랐습니다. 자동 생성 코드가 기능별 폴더에 함께 놓이지 못하는 응집성 손실은 사람이 직접 손댈 일이 거의 없는 코드라 수용 가능한 비용으로 봤습니다.

**결과**

- **납품 기간과 계약 완수**: 2개월로 산정됐던 예상 공수를 **1개월에 납품**했습니다(50% 단축). 유지보수를 포함해 **8개월 계약을 완수**했습니다.

**러닝 포인트**

- 선제 스키마 정의의 실질적 가치는 협업에서 근거를 확보하는 데 있었습니다. 미리 만들어 둔 스키마가 있으면 상대 결정에 반대할 때 의견이 아니라 검증 가능한 자료로 말할 수 있었습니다.

### §4. 번역 파이프라인 에이전트 오케스트레이션 (사이드 프로젝트)

> 번역 작업을 6개 전담 에이전트의 오케스트레이터-워커 구조로 쪼개 품질 편차를 줄였고 이 파이프라인으로 번역글 11편을 발행했습니다.

**문제**

- **일괄 처리의 품질 편차**: 영문 기술 글을 한국어로 옮기는 작업은 번역, 번역투 교정, 원문 대조, 문장 다듬기가 매번 같은 순서로 반복됩니다. 이를 한 번에 처리하면 품질이 시도마다 달라졌고 특히 "잘 읽히는가"와 "원문에 충실한가"는 서로 당기는 기준이라 한 주체가 동시에 판단하면 한쪽이 밀렸습니다.

**해결**

- **조율과 실행 분리**: 구조는 6개 전담 에이전트에 역할을 쪼개고 메인 루프는 조율만 맡는 오케스트레이터-워커 형태입니다. 메인 루프는 인자 파싱, 게이트, 점수 판정, 최종 반영만 하고 번역과 채점은 직접 하지 않습니다.
- **상충 기준의 검증 분리**: 서로 당기는 두 기준을 각각 다른 에이전트에 맡겼습니다. 한국어 품질 검토자가 번역투와 가독성을 4개 가중 차원으로 채점하고 원문 충실도 검증자는 의미와 기술 정확성, 뉘앙스를 3개 차원으로 따로 봅니다. 각자 하드 임계값에 미달하면 독립적으로 FAIL을 내며 두 검증은 서로 의존하지 않아 병렬로 호출합니다.
- **패턴 정본 단일화**: 28개 번역투 패턴은 참조 파일 한 곳을 단일 정본으로 두고 패턴 번호를 다른 파일에 복사하지 않도록 했습니다. 같은 기준이 여러 벌 존재하면 시간이 지나며 갈라지기 때문입니다.
- **난이도별 모델 배분**: 에이전트별 모델은 정의 파일의 별칭(haiku, sonnet, opus)으로 지정해 작업 난이도에 맞췄습니다. 문장 단위 패턴 검사에는 경량 모델을 붙이고 원문 대조 검증만 상위 모델이 맡습니다.

**결과**

- **발행 실적과 분류 검사**: 이 파이프라인을 거쳐 발행한 번역글은 **11편**이고 발행 분류 일관성은 CI 검사가 강제합니다.
- **점수 기반 품질 기록**: 품질 판정이 차원별 점수와 임계값으로 남습니다. 미달 시 어느 축이 부족한지가 지시로 바로 나옵니다.

**러닝 포인트**

- 처음에는 상위 모델 하나가 전 과정을 처리하는 편이 품질에 유리할 것이라 보고 메인 루프가 번역과 채점까지 직접 했습니다. 그런데 스스로 만든 결과물을 스스로 채점하면 점수가 후해졌습니다. 조율과 실행을 분리하고 채점을 별도 에이전트로 떼어낸 뒤에야 점수가 신뢰할 만해졌습니다. 검증 주체는 작업 주체와 분리해야 합니다. §1에서 이관 판단을 사람이 아닌 테스트에 맡긴 것과 같은 결론입니다.

### §5. 모노레포 아키텍처와 Core 패키지 설계 (한국기술마켓, 프리랜서 프론트엔드 엔지니어)

> Core 패키지로 공통 로직을 추출하고 공통 에러 경계를 세워 규칙 1회 수정이 8+ 앱에 일괄 반영됩니다.

**문제**

- **활용되지 못한 모노레포**: 동일한 기능에 서로 다른 UI를 배포하는 사업 특성상 유저 모노레포(**8+ 앱**), 관리자, 대시보드 **3개 레포**를 동시에 운영해야 했습니다. Turborepo 단일 구조로 묶어두기는 했지만 각 앱이 모노레포의 이점을 실제로 활용하지 못한 채 같은 로직을 앱마다 따로 들고 있었습니다.
- **규칙 변경의 반복 비용**: 공통 규칙 하나가 바뀌면 앱 수만큼 같은 수정을 반복해야 했고 어느 앱이 아직 옛 규칙을 쓰고 있는지가 코드만 봐서는 드러나지 않았습니다.
- **버튼 컴포넌트 이중화**: 프로젝트에 처음 참여했을 때 이 파편화가 버튼 컴포넌트에서 그대로 눈에 띄었습니다. 외부 패키지에도 버튼 컴포넌트가 있는데 앱 내부 디자인 시스템에도 동일한 버튼 컴포넌트가 있어 같은 UI 요소가 두 벌로 존재하는 상태였습니다.
- **FSD 도입 초기 비용**: 구조를 정리하려고 도입한 FSD는 레이어 규칙을 지키는 비용을 규칙에서 얻는 이점보다 먼저 체감하는 구간이 있어 초기 생산성을 오히려 떨어뜨렸습니다.
- **화면 단위 장애 전파**: 화면 단위 안정성에도 같은 종류의 중복이 있었습니다. 위젯 하나의 API 실패가 페이지 전체를 죽였고 화면마다 로딩과 에러 분기를 수기로 달아 보일러플레이트가 쌓였습니다.

**해결**

- **파편화 해소와 Core 패키지**: 앱마다 복제되던 공통 로직을 Core 패키지로 추출했습니다. 디자인 시스템의 헤드리스 컴포넌트와 여러 곳에 산재해 있던 재사용 커스텀 훅도 함께 모아 중앙 집중 관리 체계를 세웠습니다. 공유하는 규칙을 패키지 한 곳에서만 정의하도록 경계를 다시 그어 개별 앱에는 자기 UI 차이만 남겼습니다.
- **커스텀 레이어 재설계**: FSD 도입 초기에는 구조 자체에 매몰돼 이 컴포넌트가 정확히 어느 레이어인지를 두고 AI와 논의가 길어졌습니다. 그 끝에 구조는 개발의 목적이 아니라 수단일 뿐이라는 기준을 세우고 팀에 맞는 커스텀 레이어 변경을 제안해 승인받았습니다. 기능을 추가하는 경로에서 거쳐야 하는 레이어만 남기는 쪽으로 구조를 다시 그렸습니다.
- **공통 에러 경계 도입**: 로딩과 에러 분기를 Suspense/ErrorBoundary에 넘겨 선언적으로 흡수했습니다. 장애 영향 범위를 컴포넌트 단위로 격리해 위젯 하나의 실패가 페이지 전체로 번지지 않도록 경계를 앞당겼습니다.

**결과**

- **수정 지점 단일화**: 이제 공통 로직은 1회 수정으로 **8+ 앱**에 일괄 반영됩니다. 앱 사이에 복제해두던 코드와 파일이 줄었고 신규 앱을 붙일 때 처음부터 다시 만드는 범위도 셋업 단위로 좁혔습니다.
- **장애 격리와 보일러플레이트 제거**: 위젯 하나가 실패해도 페이지 전체가 함께 죽지 않고 화면별로 달아두던 로딩과 에러 분기 코드도 걷어냈습니다.
- **후속 파이프라인의 토대**: 정리한 3개 레포 운영 구조 위에 §2의 AI-Native 파이프라인을 올릴 수 있었습니다.

**러닝 포인트**

- FSD를 도입하고 나서 규칙을 지키는 일 자체가 목적이 되는 순간부터 아키텍처는 비용으로 돌아왔습니다. 원본 방법론을 그대로 이식한다고 팀 생산성이 오르지는 않았고 도입을 철회하는 대신 레이어를 우리 흐름에 맞게 다시 그린 판단도 이 기준에서 나왔습니다.
- 여러 앱이 코어 패키지를 공유하는 모노레포에서, 한 앱의 요구사항에 맞춰 코어 패키지 동작을 바꿨다가 다른 앱들의 빌드를 깨뜨린 적이 있습니다. 변경의 영향도를 전부 추적하지 못한 탓이었습니다. 이후 해당 앱 담당 개발자와 논의해 코어 패키지 내부 구조를 안전하게 변경하는 방향으로 해결했고 공유 패키지의 수정은 소비하는 쪽 전부를 확인한 뒤에야 안전하다는 것을 이때 배웠습니다.
- 공통 코드를 어디에 둘지는 §2와 반대 방향으로 결정했습니다. §2의 kotech-plugin은 3개 레포가 함께 쓰기 때문에 별도 레포로 분리했지만 피드백 경로가 끊기는 비용을 치렀고, Core 패키지는 소비자가 모두 같은 모노레포 안에 있어 분리하지 않는 편이 맞았습니다. 공유 코드의 배치는 소비자의 경계가 결정한다는 것을 두 경험의 차이에서 배웠습니다.

### §6. AWS 기반 프론트엔드 인프라 개선 (KC Softmax, 프론트엔드 엔지니어)

> 레포 안에 있던 번역 파일과 gRPC 스키마를 S3와 CloudFront로 빼내 번역 수정은 배포 파이프라인 밖으로, 스키마는 S3 단일 공급원 하나로.

**문제**

- **레포에 묶인 번역 파일**: 다국어 번역 파일(키와 결과값을 매핑한 파일)이 프로젝트 내부에 있었습니다. 단순한 번역 문구 하나를 고칠 때도 개발자가 직접 업데이트하고 기존의 복잡한 배포 프로세스를 거쳐야 해서 번역 관리 자체가 개발 일정에 묶여 있었습니다.
- **gRPC 스키마 수기 동기화**: gRPC는 프론트엔드와 백엔드가 동일한 스키마 파일을 공유해야 정상 동작하는데 모노레포 환경이 아니었기 때문에 매번 양쪽 레포지토리에 스키마를 일일이 배포하고 동기화해야 했습니다.

**해결**

- **번역 파일 CDN 분리**: 다국어 파일을 코드 저장소에서 들어내 S3에 올리고 CloudFront(CDN)가 앞에서 내려주도록 바꿔 번역 수정이 배포 파이프라인을 타지 않게 만들었습니다.
- **스키마 소비 시점 동기화**: gRPC 스키마 파일도 같은 방식으로 S3에 올려두고 CDN으로 배포하되 여기서는 소비 시점까지 파이프라인에 넣었습니다. 프론트엔드와 백엔드 모두 로컬 개발 서버를 실행하거나 빌드할 때 S3에서 최신 스키마를 먼저 내려받아 동기화한 뒤 빌드와 테스트를 진행하도록 구성했습니다.
- **공통 판단 근거**: 두 조치의 판단 근거는 같았습니다. 여러 저장소가 함께 쓰는 리소스를 코드 안에 두면 저장소 수만큼 사본이 생기니 리소스를 저장소 밖으로 빼고 CDN을 단일 공급원으로 삼으면 동기화라는 작업 자체가 사라집니다.

**결과**

- **비개발자 직접 반영**: 이제 비개발자도 S3에 파일을 업로드하고 수정하기만 하면 번역이 즉시 반영됩니다. CDN 캐싱 덕분에 번역 데이터를 이전보다 빠르게 받아와 렌더링합니다.
- **스키마 동기화 소멸**: gRPC 스키마는 S3를 단일 진실 공급원(SSOT)으로 삼았고 그 뒤로는 양쪽이 스키마를 맞출 일 자체가 없어졌습니다.

**러닝 포인트**

- 리소스를 CDN 뒤로 옮기고 나니 캐시 무효화가 뒤따르는 문제로 남았습니다. 번역 파일과 이미지 파일 뒤에 마지막 수정 날짜를 기반으로 한 쿼리 스트링을 붙여 해결했습니다. 값이 바뀌면 브라우저가 새 파일로 인식하고 같으면 기존 캐시를 그대로 씁니다.
- 정적 파일 배포와 CDN 캐싱이라는 요구사항이 명확해, 비용과 운영 부담이 가장 낮은 S3와 CloudFront를 곧바로 선택했습니다.
